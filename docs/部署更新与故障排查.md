# 部署、更新与排障

## 当前镜像与服务

以下来自当前 `docker-compose.yml`，不是对上游最新版本的推荐：

| 服务 | 镜像 |
| --- | --- |
| MySQL | `mysql:8.0` |
| Redis | `redis:7-alpine` |
| PostgreSQL | `postgres:16-alpine` |
| Neo4j | `neo4j:5-community` |
| Milvus | `milvusdb/milvus:v3.0.2` |
| etcd | `quay.io/coreos/etcd:v3.5.25` |
| S3 测试存储 | `adobe/s3mock:latest` |
| Prometheus | `prom/prometheus:v2.54.1` |
| Grafana | `grafana/grafana:11.2.0` |
| Jaeger | `jaegertracing/all-in-one:1.76.0` |
| 应用 | 本地构建 `tcm/backend:latest`、`tcm/frontend:latest` |

API、worker、memory-beat 以及迁移/初始化任务共用后端镜像。API/worker 共享上传卷，worker 只读。前端通过 Nginx 反代 `backend:8000`，Docker DNS 每 5 秒刷新地址，API 代理关闭缓冲以支持 SSE。

前端监听宿主机 80 端口，其余已发布的数据库和观测端口绑定 `127.0.0.1`。当前 Nginx 仅配置 HTTP；公网部署需要另行配置 TLS。S3Mock 和 Jaeger all-in-one 不是生产高可用持久化方案。

## 修改后是否需要构建

| 修改内容 | 操作 |
| --- | --- |
| Markdown 或配置注释 | 无需构建或重启 |
| 前端源码、Nginx 配置 | 构建并重建 frontend |
| 后端源码、Python 依赖 | 构建 backend，并重建 backend、worker、memory-beat |
| `.env` 配置值 | 重建使用该配置的容器；单纯 restart 不会重新加载容器环境 |
| 数据表结构/迁移脚本 | 先备份、运行对应迁移，再更新应用 |

前端更新：

```powershell
docker compose build frontend
docker compose up -d --no-deps frontend
```

无数据库结构变化的应用更新（依赖服务已经正常运行）：

```powershell
docker compose build backend frontend
docker compose up -d --no-deps --wait --wait-timeout 120 backend worker memory-beat frontend
```

已有数据需要应用记忆/接诊迁移时，先构建后端并确认 PostgreSQL/MySQL 已启动：

```powershell
docker compose build backend
docker compose run --rm --no-deps memory-migrate
docker compose run --rm --no-deps clinical-migrate
```

确认两个命令均成功后再更新应用。MySQL `init/` 脚本仅在空数据卷首次初始化时执行，不会在每次启动时升级已有表。不要用删除数据卷代替迁移。

不带服务名的 `docker compose up -d` 会处理整套编排，可能再次启动已退出的初始化任务。当前向量导入会追加重复记录，应用更新优先使用上述定向命令，详见 [知识入库](知识入库与数量核验.md)。

Docker Hub 不可用、但本机已有 `tcm/frontend:latest` 和前端依赖时，可使用已有镜像构建：

```powershell
Push-Location frontend
npm run build
Pop-Location
docker build --pull=false -f frontend/Dockerfile.prebuilt -t tcm/frontend:latest frontend
docker compose up -d --no-deps frontend
```

必须确认 `npm run build` 成功才继续复制产物。部署完成后浏览器可用 `Ctrl+F5` 刷新。

## 日志与故障定位

```powershell
docker compose ps -a
docker compose logs -f --tail=200 backend worker
docker compose logs --tail=100 frontend memory-migrate clinical-migrate neo4j-init
Invoke-RestMethod http://localhost:8000/healthz
Invoke-RestMethod http://localhost:8000/readyz
```

不在项目目录也可按容器名查看 API 日志：

```powershell
docker logs -f --tail=200 zhizhen-backend-1
```

| 现象 | 优先检查 |
| --- | --- |
| 登录无反应、Nginx 502 / connection refused | backend 是否运行并监听 8000；backend 启动日志；前端 Nginx 是否包含 Docker DNS 更新配置 |
| `memory-migrate` 或 `clinical-migrate` exit 1 | 对应迁移日志、数据库健康状态、连接配置及权限；成功的一次性任务应为 Exited (0) |
| Neo4j / Milvus unhealthy | 对应服务日志；Milvus 的 etcd、s3、卷权限初始化及启动等待时间 |
| `all vision models failed` | worker 日志和图片任务状态；主/备用模型是否支持图像、接口地址、API key、超时与供应商响应 |
| 报告显示等待医生确认 | 检查患者是否授权医生、医生是否接诊并确认发布；此状态不代表生成失败 |
| 报告加载失败 / SSE 处理失败 | 浏览器请求及 backend 错误；SSE 在 HTTP 200 后也可能返回业务 error 事件 |
| 删除失败 | backend 日志；MySQL 外键/事务错误、PostgreSQL 可用性、是否收到 409 会话处理中；失败后核查两库实际状态 |
| 历史记录数量少 | 当前用户/租户、是否已删除，以及接口最近 100 条限制；不要直接认定数据库记录丢失 |

日志排查使用请求 `X-Trace-Id` 关联 structlog 与 Jaeger。图片模型调用发生在 worker，不能只看 frontend 访问日志。API 存活检查通过也不等于全部业务依赖就绪。

## 可观测配置

- Prometheus 抓取 API `/metrics`；Grafana 使用仓库内数据源与大盘配置。
- Jaeger UI：`http://localhost:16686`。默认根请求采样率 `OTEL_SAMPLE_RATIO=0.1`，不是每次请求都有采样链路。
- `LANGSMITH_TRACING=true` 并设置 `LANGSMITH_API_KEY` 后启用模型调用追踪，默认隐藏输入输出；关闭时不应依赖 LangSmith 查问题。
- 日志写 stdout；长期日志检索需另外配置集中存储。worker 进程指标当前没有独立 Prometheus 导出端点。
- backend 固定宿主机端口 8000，不支持直接用 `--scale backend=2` 完成多副本部署；需先设计网关、端口和指标抓取。worker 可按任务容量扩容。

## 验证

文档/注释更新不需要重新构建应用。应用代码变更可执行前端类型检查和生产构建：

```powershell
Push-Location frontend
npm run build
Pop-Location
```

后端独立测试编排使用临时 PostgreSQL，不挂载业务数据卷：

```powershell
docker build -t tcm/backend:enterprise-test ./backend
docker compose -f docker-compose.test.yml up --abort-on-container-exit --exit-code-from tests
docker compose -f docker-compose.test.yml down
```

`RUN_POSTGRES_TESTS=1` 的测试会清空测试库的 `agent_memory`，不得改为连接业务 PostgreSQL。删除验收只使用测试用户与测试会话，不要拿真实患者记录验证。

## 数据保留与恢复边界

`docker compose down` 停止服务并保留命名卷；`down -v` 会删除数据卷，不是正常更新步骤。备份应覆盖 MySQL、PostgreSQL、Neo4j、Milvus/etcd/S3 存储、上传卷及原有加密密钥，并验证恢复流程。

`ENCRYPTION_KEY` 丢失或直接替换会导致既有密文无法解密。记忆默认短期 24 小时、长期 365 天；`memory-beat` 每小时触发到期记忆清理。业务表 `DATA_RETENTION_DAYS` 尚未接通统一自动清理，不应据此承诺全部健康数据到期删除。
